## 0. 要交出什麼

9 個 PR（一個 PR 一個分支、base `main`、前一個合併後才開下一個），做完時 **72 隻每一隻都用骨架木偶**，
而且每一隻的動作是照「牠的外型在現實世界最像的那種動物」怎麼動來做的——**不是**「每隻套同一套走路，換個步幅」。

使用者最在意、最怕的失敗：**動作不像真的動物**（還是斷手斷腳、一整塊硬的在轉、每隻都一樣）。這份規格其他的東西都是為了擋這一條。

## 1. 「像真的動物」的唯一定義（每一批都用這個，做之前就定好）

一隻算「做完」要**三條都成立**：

1. **動作卡**（§4）在標關節**之前**寫好：現實裡最像的動物、步態、踩地比例、腳落地順序、身體姿勢、哪些部位是被動跟著甩的、出處。
2. **量得到的條件都過**（§5 的檢查從骨架實際畫出來的畫面量，不是從參數表抄）。
3. **使用者看過這一批的總表＋新舊並排影片**，說「像」。

少一條就不算做完。**不准**用「看起來還可以」取代第 2 條，也不准在使用者看之前說「做完了」。

## 3. 架構規則（一條，可以 grep）

**物種專屬的東西只能出現在 `skeletons.js`**。`skeleton.js` 裡不准出現物種編號或名字：

```bash
grep -nE "\b(6[5-9][0-9]|7[0-2][0-9])\b" src/renderer/gfx/skeleton.js   # 應該沒有結果（行號、常數除外要人工看一眼）
```

引擎提供「動法」（兩腳、四腳、翅膀、鏈、身體波…），物種在 `skeletons.js` 選用哪一種、參數多少。
引擎裡出現「如果是甲賀忍蛙就…」＝設計錯了：下一隻長得像的就用不到，而且改一隻會壞另一隻。

## 4. 動作卡（每一隻、標關節之前寫；放在 `skeletons.js` 那一筆的註解裡）

```js
// 動作卡：像 <現實動物>（<出處簡稱>）
//   移動：<步態>，<腳落地順序>，踩地比例 <duty>，慢走 → 快跑怎麼換
//   身體：<前傾角度／水平／直立>，<起伏：最低在哪一刻>，<左右晃或不晃>
//   被動跟著動的：<尾巴、耳朵、緞帶、垂掛物…>（延遲多少、從哪往哪傳）
//   做不到的：<外型限制，例：大腿很大只能小步走>
```

規則：
- **「像什麼動物」要是真的動物**，不是別的寶可夢、不是「一般四腳獸」。找不到依據就 research，寫出處；真的沒有就寫「猜的」並列進 PR 描述。
- 同一批裡**兩隻的動作卡不能一模一樣**。長得像（例：672／673 小羊和山羊）也要寫出差在哪（大小 → 步頻、重量 → duty）。
- 外型做不到動作卡的動作（IK 解不出來、會扯裂）：**寫進「做不到的」，改成外型做得到的最接近的動作**，不要硬做到扯裂，也不要偷偷退回「整塊平移」。

## 5. 失敗模式（先講好，看到症狀就知道是哪一個）

**FM1 每隻都一樣。** 症狀：總表裡同一批的走路只差步幅。機制：只調 `strideK` 不寫動作卡，沿用預設步態。
檢查：每一筆 `skeletons.js` 都有動作卡；同一批沒有兩筆的 `gait`／`duty`／`phase` 組合完全相同（除非動作卡寫了理由）。

**FM2 斷手斷腳（一整塊硬的在轉）。** 症狀：手腳像木棍繞根部轉，膝蓋、手肘不彎。機制：手腳只標 2 個點（一段）。
檢查：動作卡說會彎的手腳至少 3 個點（2 段）；只有動作卡寫「硬的」（劍、盾、角）才准一段。

**FM3 腳滑。** 症狀：身體往前、踩地的腳也跟著往前滑。機制：步幅 `info.stride` 跟動畫推步相的距離對不上。
檢查：`test/e2e/natural.cjs` 的 M2（腳打滑）門檻不放寬；新的動法（跳、爬、翅膀）要同樣照走的距離推步相。

**FM4 扯裂、散落的點、露洞。** 症狀：關節旁邊出現透明縫、一兩格顏色留在原地、手腳移開露出空白。
機制：框標錯（少一格／多框到身體）、蒙皮範圍不夠、手腳底下沒補。
檢查：用骨架上色圖（每格照骨頭上色、alpha 不變）找出那一格歸誰，**先找原因再改**（PR #49 找到的真正原因都是「框差一格」「外框線另一邊是身體」，不是演算法）。
**不准**用加大 `FILL`、`MARGIN` 蓋過去。

**FM5 該甩的東西是死的。** 症狀：尾巴、緞帶、觸手、鑰匙跟身體一起硬轉或完全不動。機制：鏈沒有延遲，只是一個角度。
檢查：鏈的末端相對根部有相位延遲（量畫出來的末端位置：身體停下後末端還會晃，晃的時間 > 0）。

**FM6 整張圖縮放、任意旋轉。** 規格 F7：整張圖只准翻面、轉 90° 的倍數。跳的「壓扁」要用身體下沉、腳彎，**不准 scale**。
檢查：`natural.cjs` 的 M7 照舊。

**FM7 動法用錯。** 症狀：小鳥用走的（應該跳）、狗用貓步（應該小跑）、胖的走得像瘦的（應該搖擺）。機制：沒查就用預設。
檢查：動作卡的出處。**這是使用者最怕的那一種失敗，寧可多查一次**。

## 6. 每一批要交的東西（驗收條件）

1. `skeletons.js`：這一批每一隻一筆（`size`、關節、外框、動作卡）。
2. 引擎：這一批表上寫的那種動法，接在 `skeleton.js`，其他物種的畫面**不變**（用 `scripts/skeleton/skelshot.cjs` 前後各產一張，沒改到的物種要一模一樣）。
3. 總表 `docs/screens/skeleton-<批名>.png`（`scripts/skeleton/skelshot.cjs`）：骨架疊在原圖上＋這一批的主要動作一輪。
   預期：兩腳的看得到膝蓋彎、腳一步一步踩；翅膀的看得到往下拍比往上收久；鏈的看得到末端比根部晚。
4. 新舊並排影片（`scripts/skeleton/walkvid.cjs`），放 `.cache/`（不進 repo），在回報裡給路徑。
5. README 的骨架木偶段落補這一批的動法、猜的數字、限制、參考。
6. 測試：`puppet.cjs`、`natural.cjs`、`menu.cjs` 和全部 e2e、全部單元測試；**門檻不准放寬**，改量法要寫改前改後。
7. 真的 Electron 跑一次：**先用 `.cache/skel/electron-main.mjs`（`app.setPath('userData', 暫存資料夾)`）**，確認暫存資料夾有東西、使用者的 `save.json` 時間沒變才開始點（**不准**用改 `APPDATA` 的方法，那樣擋不住，PR #49 時開到過使用者真的存檔）。
8. PR 描述：動作卡摘要表（每隻一行：像什麼動物、步態）、猜的數字、沒過的測試照實寫。

## 7. 停下來問的點（預算）

- **每一批標完、總表和影片做好後，停下來給使用者看，等「像」再開 PR。** 不要一路做到開 PR 才給看。
- 一隻的動作卡做不到、改了 2 次還是扯裂或不像：**停下來**，給使用者看骨架上色圖和這一隻的總表，說你想怎麼改（改動作卡／改標記／接受限制），不要自己換成更簡單的動作。
- 一個 PR 修改的既有檔案要超過 12 個：停下來列清單問。
- 一批 e2e 全部跑完多超過 3 分鐘（目前約 8 分鐘）：停下來說明。

## 8. 這個改變在別的地方的代價

- 骨架的圖四周多留 10 格（自動木偶 4 格），`pet.js` 的位置、點擊、拎起來、影子已經扣掉（`info.trim`）。
  別的檔案用 `asset.w`／`asset.h` 算間距、特效位置的會寬一點——**不要**這幾個 PR 順便去改那些檔案（超過 12 個檔案、不是這件事）。
- 自動木偶（`rig.js`）做完 9 批後就沒有物種在用了，**不要刪**，也不要在這 9 個 PR 裡改它（替代圖、圖大小不對時還會用到；要不要刪之後問使用者）。
- 步相 `gait` 是繞圈的，一幀最多走 1 格（`PuppetView.drive`）；新的動法（拍翅、身體波）如果也有繞圈的相位，一樣要放進 `info.cyclic`，不然 M8 會把 15→0 算成跳 15 級。

「延遲甩的一串」別人的做法是 follow-the-leader（後一節延遲跟前一節）。我們的姿勢圖是**照參數快取的**，
**不要**做成每幀積分的 verlet（快取會爆、同一組參數畫出不同圖，M8 會壞）。

實際做法（PR 1 定案，跟原本寫的「相位波」不一樣，理由如下）：尾巴、耳朵的擺動不只來自動作組的週期，
習性會直接指定甩法、身體往前晃也會帶動尾巴往後甩，這些不是週期的，相位波做不到。所以改成
`gfx/sprites.js` 的 `PuppetView` **記住根部（tailSw、earSw）最近的級數，第 j 節用「j × `LAG_S` 秒前」的**（真正的 follow-the-leader）。
延遲後的角度一樣量化、接在 `quantize` 的 key 後面：同一組參數永遠畫出同一張圖；每一節每幀最多變 1 級（M8）。
固定畫面（野生的、`sets[].frames`）沒有記錄，每一節都用現在的，跟以前一樣。
布（袍子下襬）是跟著步伐鼓的，這種才用照步相的相位波（`CLOTH_LAG`）。

## 10. 每一批的做事順序（第一個失敗會自己指出是哪裡）

1. **寫這一批每一隻的動作卡**（還不碰程式）→ 給使用者看表（一隻一行）。動作用錯（FM7）在這一步最便宜。
2. **引擎先只接一隻最簡單的**，量 §5 的條件、看骨架上色圖。這一隻不過，問題在引擎，不在標記。
3. 其他隻一隻一隻標：`scripts/skeleton/grid.cjs <編號>` 放大加格線 → 標 → `one.cjs` 看關鍵的幾格 → 上色圖找散落點。
4. 總表＋影片 → **停下來給使用者看**（§7）。
5. 使用者說像 → 全部測試 → 真的 Electron → README → PR。

## 11. 工作方式

- 不加 npm 依賴、不用 API key（CLAUDE.md §1）。要裝什麼先問。
- 每個檢查點 commit 一次，繁體中文寫清楚做了什麼、為什麼；commit／PR 不寫模型名稱。
- 猜的數字一律 `// 猜的，可調整`，PR 描述列全部。
- 動作不對時，**先給使用者看總表或上色圖再改參數**；一次只改一個東西，不然不知道是哪個改好的。
